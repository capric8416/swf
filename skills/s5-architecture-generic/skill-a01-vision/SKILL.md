## 触发条件

当满足以下任一条件时，触发本 Skill：

1. 需求分析阶段已完成，获得软件需求规格说明书（SRS）
2. 需要基于需求自动推导架构方向
3. 需要明确架构关键决策点

## 执行流程

### 步骤 1：读取并分析需求产物

自动读取需求分析阶段的产物：
- 需求规格说明书（SRS）
- 用户故事清单
- 非功能需求
- 约束条件

### 步骤 2：自动识别系统特征

基于需求内容自动分析系统特征：

| 分析维度 | 分析内容 | 输出 |
|----------|----------|------|
| **系统类型** | Web应用/移动应用/桌面应用/嵌入式/大数据 | 系统类型判定 |
| **用户规模** | 内部使用/部门级/企业级/互联网级 | 规模等级判定 |
| **数据特征** | 数据量、数据类型、数据关系复杂度 | 数据特征判定 |
| **性能要求** | 响应时间、并发量、吞吐量要求 | 性能等级判定 |
| **集成需求** | 外部系统数量、集成复杂度 | 集成等级判定 |
| **安全等级** | 公开/内部/敏感/机密 | 安全等级判定 |

### 步骤 3：自动推导架构方向

基于系统特征自动推导架构建议：

**系统类型 → 架构风格推荐**

| 系统类型 | 推荐架构风格 | 理由 |
|----------|--------------|------|
| 企业Web应用 | 分层架构 | 结构清晰，易于维护 |
| 高并发互联网应用 | 微服务架构 | 水平扩展，独立部署 |
| 实时数据处理 | 事件驱动架构 | 异步处理，高吞吐 |
| 复杂业务系统 | 领域驱动设计 | 业务对齐，易于演进 |
| 移动端应用 | 前后端分离 + BFF | 适配多端，统一接口 |

**性能等级 → 技术策略**

| 性能等级 | 推荐策略 |
|----------|----------|
| 低（<100并发） | 单体应用，简单缓存 |
| 中（100-1000并发） | 应用集群，数据库优化 |
| 高（1000-10000并发） | 分布式缓存，读写分离 |
| 极高（>10000并发） | 微服务，分库分表，消息队列 |

**数据特征 → 存储方案**

| 数据特征 | 推荐存储方案 |
|----------|--------------|
| 关系型数据为主 | 关系数据库（PostgreSQL/MySQL） |
| 文档型数据为主 | 文档数据库（MongoDB） |
| 海量日志数据 | 时序数据库（InfluxDB/TimescaleDB） |
| 复杂关系查询 | 图数据库（Neo4j） |
| 混合数据类型 | 多存储组合（Polyglot Persistence） |

### 步骤 4：识别需要用户确认的决策点

自动识别需求中不明确或需要权衡的决策点：

**常见决策点清单：**

1. **架构风格选择**
   - 当系统同时具有多种特征时
   - 需要用户确认最终选择

2. **技术栈选择**
   - 当存在多个同等可行的技术选项时
   - 需要用户基于团队能力选择

3. **部署方式**
   - 云原生 vs 传统部署
   - 需要用户基于基础设施选择

4. **数据一致性策略**
   - 强一致性 vs 最终一致性
   - 需要用户基于业务容忍度选择

5. **安全等级**
   - 当安全需求描述模糊时
   - 需要用户明确安全要求

### 步骤 5：用户交互确认

针对识别出的决策点，与用户交互确认：

**交互方式 1：提供选项**

```
基于需求分析，系统具有以下特征：
- 系统类型：企业Web应用
- 用户规模：部门级（约500用户）
- 性能要求：中等并发（约200并发）

推荐架构方案：
A. 分层架构 + 单体部署（推荐）
   - 适合当前规模，开发效率高
   - 未来可平滑演进为微服务
   
B. 微服务架构 + 容器部署
   - 适合未来扩展，但初期复杂度高
   - 需要DevOps能力支持

请选择架构方案（A/B）：
```

**交互方式 2：询问澄清**

```
需求中提到"系统需要支持高可用"，但未明确可用性指标。

常见可用性等级：
- 99.9%（年停机时间 < 8.76小时）- 一般业务系统
- 99.99%（年停机时间 < 52.6分钟）- 重要业务系统
- 99.999%（年停机时间 < 5.26分钟）- 核心业务系统

请确认系统的可用性要求：_____
```

**交互方式 3：确认假设**

```
基于需求分析，做出以下假设：

假设 1：系统主要面向内部用户，不需要考虑CDN加速
假设 2：数据增长率为每月10%，3年内数据量在可管理范围
假设 3：系统集成主要通过REST API，不需要消息队列

请确认以上假设是否成立（是/否）：
如有不成立的假设，请说明：_____
```

### 步骤 6：生成架构愿景

基于自动分析和用户确认，生成架构愿景：

**架构愿景内容包括：**

1. **系统定位**
   - 系统类型和范围
   - 目标用户群体
   - 核心价值主张

2. **架构目标**
   - 功能性目标
   - 非功能性目标（性能、可用性、安全性等）
   - 目标优先级

3. **架构原则**
   - 基于系统特征选择适用的原则
   - 原则优先级

4. **关键决策**
   - 已确认的架构决策
   - 决策理由

5. **风险与假设**
   - 识别的架构风险
   - 设计假设

### 步骤 7：用户评审

生成架构愿景初稿后，进入用户评审：

**评审内容：**
1. 系统定位是否准确
2. 架构目标是否完整
3. 关键决策是否合理
4. 风险识别是否充分

**评审选项：**
- **确认** → 进入步骤 8
- **修改：{具体意见}** → 返回步骤 5-6 调整
- **补充：{新增内容}** → 补充分析后重新评审

### 步骤 8：生成产物

评审通过后，生成以下产物：

1. **架构愿景文档**（Markdown 格式）
2. **更新 Todo-List**：标记 S5-A01 为已完成

---

## 决策点识别规则

### 自动判定 vs 用户确认

| 场景 | 处理方式 | 示例 |
|------|----------|------|
| 特征明确且唯一 | 自动判定 | 小型内部工具 → 单体架构 |
| 特征明确但有多个选项 | 提供选项供选择 | Web应用 → 分层/微服务 |
| 特征不明确 | 询问澄清 | "高性能"具体指标 |
| 需要权衡 | 列出利弊供决策 | 一致性 vs 可用性 |

### 决策优先级

| 优先级 | 决策项 | 影响 |
|:------:|--------|------|
| P0 | 架构风格 | 全局影响，难以变更 |
| P1 | 技术栈 | 影响开发效率和团队学习成本 |
| P2 | 部署方式 | 影响运维复杂度 |
| P3 | 详细设计 | 可在实现阶段调整 |

## 错误处理策略

| 错误场景 | 处理策略 |
|----------|----------|
| 需求产物缺失 | 提示用户先完成需求分析阶段 |
| 需求描述模糊 | 列出可能的解释供用户选择 |
| 用户选择冲突 | 分析冲突原因，提供权衡建议 |
| 技术选项过多 | 基于常见实践筛选2-3个最佳选项 |

---

## 注意事项

1. **自动推导为主，用户确认为辅**：优先基于需求自动推导，减少用户负担
2. **提供理由**：每个推荐都应附带理由，帮助用户理解
3. **保持开放**：用户可以选择不同于推荐的方案
4. **记录决策**：所有决策（自动或人工）都应记录理由
5. **迭代优化**：根据用户反馈持续优化推导规则
