### 步骤 3：自动设计表结构

#### 3.1 表命名规范

| 规范项 | 规则 | 示例 |
|--------|------|------|
| 表名 | 小写，下划线分隔，复数名词 | `users`, `order_items` |
| 主键 | `id` | `id` |
| 外键 | `{关联表}_id` | `user_id`, `order_id` |
| 关联表 | `{表 1}_{表 2}`（按字母序） | `user_roles`, `order_products` |
| 审计字段 | `created_at`, `updated_at`, `deleted_at` | 标准时间戳 |

#### 3.2 字段设计规范

**标准字段类型映射：**

| 编程语言 | 数据库类型 | 说明 |
|----------|------------|------|
| string | VARCHAR(n) | n 根据业务长度确定 |
| text | TEXT | 长文本内容 |
| number | DECIMAL/INT | 根据精度选择 |
| boolean | BOOLEAN/TINYINT | 布尔值 |
| date | DATE | 日期 |
| datetime | DATETIME/TIMESTAMP | 时间戳 |
| array | JSON | 数组或复杂结构 |

**字段设计原则：**

| 原则 | 说明 | 示例 |
|------|------|------|
| 原子性 | 字段不可再分 | `first_name`, `last_name` 而非 `full_name` |
| 明确性 | 字段名表达清晰 | `status` 而非 `col1` |
| 一致性 | 相同含义字段同名 | 所有外键统一用 `{table}_id` |
| 适度冗余 | 为性能适当冗余 | 订单表冗余用户姓名 |

#### 3.3 表结构模板

**标准表结构：**

```
表名：users
描述：用户信息表

字段清单：
├── id: BIGINT, 主键，自增
├── username: VARCHAR(50), 非空，唯一，用户名
├── email: VARCHAR(100), 非空，唯一，邮箱
├── password_hash: VARCHAR(255), 非空，密码哈希
├── nickname: VARCHAR(50), 可空，昵称
├── avatar_url: VARCHAR(255), 可空，头像 URL
├── status: TINYINT, 非空，默认 1，状态（1 正常 0 禁用）
├── created_at: DATETIME, 非空，创建时间
├── updated_at: DATETIME, 非空，更新时间
└── deleted_at: DATETIME, 可空，删除时间（软删除）

索引：
├── PRIMARY KEY (id)
├── UNIQUE KEY uk_username (username)
├── UNIQUE KEY uk_email (email)
└── KEY idx_status (status)

约束：
├── CHECK status IN (0, 1)
└── CHECK email 格式验证
```

### 步骤 4：自动设计索引

#### 4.1 索引设计规则

| 场景 | 索引策略 | 说明 |
|------|----------|------|
| 主键 | 聚簇索引 | 默认创建 |
| 外键 | 普通索引 | 优化关联查询 |
| 唯一字段 | 唯一索引 | 保证唯一性 |
| WHERE 条件 | 普通索引 | 加速查询 |
| ORDER BY | 普通索引 | 避免排序 |
| GROUP BY | 普通索引 | 加速聚合 |
| 多条件组合 | 复合索引 | 最左前缀匹配 |
| 模糊查询 | 全文索引 | LIKE '%text%' |

#### 4.2 复合索引设计原则

| 原则 | 说明 | 示例 |
|------|------|------|
| 最左前缀 | 索引字段顺序重要 | (a,b,c) 支持 a, ab, abc 查询 |
| 选择性高 | 区分度高的字段在前 | 状态字段在后 |
| 等值优先 | 等值条件字段在前 | WHERE a=1 AND b>2，a 在前 |
| 避免冗余 | 不复盖已存在的索引 | 已有 (a,b)，不再建 (a) |

#### 4.3 索引设计模板

```
表：orders

索引设计：
├── PRIMARY KEY (id)
│   └── 聚簇索引，主键
├── UNIQUE KEY uk_order_no (order_no)
│   └── 唯一索引，订单号
├── KEY idx_user_id (user_id)
│   └── 普通索引，用户查询订单
├── KEY idx_status_created (status, created_at)
│   └── 复合索引，按状态和时间筛选
└── KEY idx_created_at (created_at)
    └── 普通索引，时间排序

索引选择理由：
- uk_order_no: 订单号查询频繁，需要唯一性保证
- idx_user_id: 用户查询订单高频场景
- idx_status_created: 后台管理按状态筛选订单
- idx_created_at: 按时间排序展示
```

```
视图名：v_order_detail
描述：订单详情视图（订单 + 用户 + 商品）

CREATE VIEW v_order_detail AS
SELECT 
    o.id AS order_id,
    o.order_no,
    o.total_amount,
    o.status,
    o.created_at,
    u.username,
    u.nickname,
    oi.product_id,
    oi.product_name,
    oi.quantity,
    oi.price
FROM orders o
JOIN users u ON o.user_id = u.id
JOIN order_items oi ON o.id = oi.order_id;

使用场景：
- 订单列表查询
- 订单详情展示
- 后台订单管理

注意事项：
- 视图仅用于查询，不用于更新
- 大数据量场景考虑物化视图
```

## 用户交互

### 交互时机

在步骤 10 触发用户交互，以下场景需要用户确认：

1. **信息完整度不足**：实体属性信息不足以推导表结构
2. **需求理解模糊**：数据规模、性能要求不明确
3. **用户偏好不明确**：数据库选型、索引策略存在多个可行方案
4. **发现重大设计风险**：识别到可能影响项目的数据库设计决策

### 交互方式

**方式 1：提供选项**

当存在多个可行方案时，提供选项供用户选择：

```
基于数据特征分析，"订单数据存储"推荐以下方案：

A. 单一订单表（推荐）
   - 所有订单在同一张表
   - 简单，易于维护
   - 适合数据量 < 5000 万
   
B. 按状态分表
   - 进行中订单表 + 已完成订单表
   - 提高查询性能
   - 增加应用复杂度

C. 按月分表
   - 每月一张订单表
   - 便于历史数据归档
   - 跨月查询复杂

请选择存储方案（A/B/C）：
```

**方式 2：询问澄清**

当需求描述不明确时，询问用户澄清：

